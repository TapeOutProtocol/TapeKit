# DeWEB 跨链消息层 —— 设计说明（草案 1，2026-09-18）

> 目标：让任何公链上的电路容器，都能用一个全网唯一的地址互相收发消息。
> 不用跨链桥、不用索引器、不用服务器：每条消息在它所在的那条 L1/L2 上直接执行和验证，
> 收件人的客户端去各条链上读取、合并。
>
> 本文是 TAP-10 v1.0 的设计依据。确认后再改规范、合约、模块和客户端。

---

## 0. 一句话架构

```
   BNB Chain                 Base                   X Layer
 ┌───────────┐          ┌───────────┐          ┌───────────┐
 │ DeWEB 中枢 │          │ DeWEB 中枢 │          │ DeWEB 中枢 │   ← 每条链一份，地址完全相同
 │ 0xHUB…    │          │ 0xHUB…    │          │ 0xHUB…    │
 │ 链上信箱   │          │ 链上信箱   │          │ 链上信箱   │   ← 收件目录/发件目录直接存在合约里
 └─────▲─────┘          └─────▲─────┘          └─────▲─────┘
       │ 本链身份核对+写入       │                      │
       │                      │                      │
   发件人在「自己的链」上发       收件人的客户端依次读各链中枢的「我的信箱」，按时间合并
```

- **写**：发件人永远在**自己容器所在的链**上发交易。中枢只在本链核对身份（和现在一样），不依赖任何别的链。
- **读**：收件人客户端向每条链的中枢问「发给我的消息有哪些」，按时间合并成一个列表。
- **公钥**：只存在收件人**自己的主链**上。发件人客户端跨链读取（读取免费，客户端本来就能读任何链）。

没有桥，所以没有桥的信任假设、桥费和桥被盗的风险。

## 1. 全网唯一的端点地址

### 1.1 机器形式：32 字节端点号

```
端点号 (bytes32) = uint32(0) ‖ uint64(chainId) ‖ address(容器)
                 高 4 字节保留为 0 │ 8 字节链号 │ 20 字节容器地址
```

- 容器是 ERC-6551 账户，它的地址计算本身就包含 chainId，**不同链上的容器地址不会相同**；
  再把 chainId 显式写进端点号，任何人不需要任何中心登记就能保证全网唯一。
- 合约、事件、加密绑定、客户端内部一律使用端点号。

### 1.2 显示形式

| 显示 | 含义 |
|---|---|
| `#15324@30` | BNB Chain 上的 #15324@30（BNB 为主链，保留短写，兼容现有写法） |
| `#15324@30.base` | Base 上的 |
| `#15324@30.xlayer` | X Layer 上的 |

- 链的短名**只能**取自规范里的「链表」（§6），不接受任意文本，防止用相似名字仿冒。
- 链上网站的主机名同步扩展：`15324.30.tape`（BNB）、`15324.30.base.tape`。需要同步修改 SPEC.md（tape:// 规范）。

## 2. 链上信箱（取代索引器）

### 2.1 存储

每条消息在**发出它的那条链**的中枢里写 3 个存储槽：

| 位置 | 内容（打包成槽） |
|---|---|
| `inbox[to][i]` 槽 1 | `from`（20 字节，本链容器）‖ `block`（uint56，7 字节）‖ `timestamp`（uint40，5 字节），恰好 256 位 |
| `inbox[to][i]` 槽 2 | `digest = keccak256(ref ‖ keccak256(payload))` |
| `outbox[from][j]` | `to`（28 字节端点号）‖ `i`（4 字节，该消息在对方信箱里的序号） |
| `inboxCount[to]`、`outboxCount[from]` | 计数 |

`to` 是 32 字节端点号，可以指向**任何链**上的容器。

### 2.2 读取

| 读取函数 | 返回 |
|---|---|
| `inboxCount(bytes32 to)` | 本链上发给 `to` 的消息总数 |
| `inboxPage(bytes32 to, uint256 start, uint256 n)` | 第 `start` 起 `n` 条的（from, block, timestamp, digest） |
| `outboxCount(address from)` / `outboxPage(...)` | 发件目录 |

- **列表**：全部用 `eth_call` 读合约存储，**所有公共节点都支持**，多节点严格一致很便宜。
- **完整性**：有了总数，客户端能确认「一条不漏」。这是索引器做不到的（索引器最多只能漏报，但你发现不了）。
- **打开一条消息**：按存储里的区块号，从**任意一个**节点取该区块的日志，找到对应的 `Sent` 事件，
  用 `digest` 核对载荷和 `ref`。节点撒谎 → 哈希对不上 → 换一个节点。载荷真实性由链上存储保证。
  匹配日志时必须同时核对收件端点、发件容器、信箱序号，**不能只凭 digest 匹配**（digest 只绑定 ref 和载荷，别人可以原样重放同一份载荷）。
  日志里的交易哈希只是线索（txHint），要用它（例如核对附件付款人）必须多节点严格读回执再确认。

### 2.3 实测过的节点能力（2026-09-18）

| 节点 | 按区块号取日志 `eth_getLogs(fromBlock=toBlock=区块号)` | 整块收据 `eth_getBlockReceipts` |
|---|---|---|
| bsc-dataseed.bnbchain.org | ✗（limit exceeded） | ✓ |
| bsc-rpc.publicnode.com | ✓ | ✓ |
| bsc-dataseed1.defibit.io / ninicoin.io | ✗ | ✓ |
| mainnet.base.org | ✓ | ✗ |
| base-rpc.publicnode.com | ✓ | ✓ |
| rpc.xlayer.tech / xlayerrpc.okx.com | ✓ | ✓ |

所以「打开消息」两种方式都实现，按节点自动选择。整块收据每块约 10–110 KB，只在打开消息时取一次，可接受。

### 2.4 成本

每条消息比现在多约 7–8 万 gas（3 个新槽 + 2 个计数）。按 BNB 0.05 gwei、BNB 725 美元估算，
**每条多约 0.003 美元**，由发件人付。Base、X Layer 更便宜。16 KB 的消息本身的数据费远大于这部分。

## 3. 跨链发送的完整流程

以 Base 上的 A（`#7@2.base`）发给 BNB 上的 B（`#15324@30`）为例：

1. A 的客户端解析 B：到 **BNB** 上读 B 的容器、公钥记录（多节点严格一致，和现在一样）；
2. 检查 B 公钥记录里的「收信链」（§4）包含 Base；不包含就拦下并说明原因；
3. A 用 B 的公钥密封消息，认证数据绑定：`to`（B 的端点号）、`from`（A 的端点号）、`ref`、**发出链的 chainId**、中枢地址；
4. A 在 **Base** 上调用 `send(A 的处理器合约, A 的 #ID, B 的端点号, ref, payload)`；
   Base 中枢在 Base 上核对 A 是持有人、已开通；写入 `inbox[B]`、`outbox[A]`；
5. B 的客户端读 BNB、Base、X Layer 三个中枢的 `inbox[B]`，合并，按时间排序显示；
6. B 回复：B 在 **BNB** 上发，`to` = A 的端点号（Base）。A 的客户端在 BNB 的中枢里读到。

每一步都只在一条链上执行，没有任何跨链调用。

## 4. 公钥记录的变化

`publishKey` 多一个参数：**收信链位图** `uint64 chains`（位 k = 链表第 k 条链）。

- 收件人声明「我读哪些链的消息」。发件客户端只允许从位图里的链发送，免得消息发到收件人不读的链上。
- 也是垃圾消息的开关：不想收某条（便宜的）链上的消息，就把它去掉。
- 公钥只存在收件人的主链。一个人在两条链上各有一个容器，就是两个独立身份。

## 5. 各链中枢地址相同

现在中枢的代理地址取决于实现地址，而实现的构造参数（工厂、付费表等）每条链不同，所以地址会不同。改法：

1. 先用 CREATE2 部署一个**与链无关的启动实现**（没有构造参数，每条链地址相同）；
2. 代理指向启动实现、初始化 owner → 代理地址 = f(部署器, 盐, 启动实现, owner)，**每条链相同**；
3. owner 再把代理升级到该链的正式实现（各链构造参数不同，没关系）。

已核实：确定性部署器 `0x4e59…956C` 和 ERC-6551 注册表 `0x0000…5758` 在 BNB、Base、X Layer 上都已存在。

代价：**BNB 上刚部署的测试中枢 `0x3A27…965B` 要作废、按新方式重新部署**（新地址）。
现在还没有真实用户，这是换掉它成本最低的时候。

- 新增一条链 = 规范加一行 + 部署中枢。旧客户端不认识新链时，发件方会因「收信链」位图拦下，不会静默丢消息。
- 每条链至少配置 2 个不同运营方的公共节点（严格一致的前提）。

## 7. 安全与边界（必须讲清楚的）

1. **这是「端点之间」的消息层，不是「合约之间」的跨链调用。**
   人、Agent、应用的客户端能跨链读取并验证所有消息。但 **A 链上的合约无法读取 B 链上的消息**——
   合约看不到别的链，这是 L1 的物理限制。需要在另一条链上「执行动作」时，由收到消息的一方
   在那条链上自己发交易（例如：看到付款请求后在本链付款）。宣传时不要说成「合约可以跨链互调」。
2. **每条链各自的信任**：每条链的中枢要各自封印；每条链的 TapeOut 工厂要各自封印。
   任何一条链未封印，来自那条链的消息都要带警告（与现在同一套规则，按链分别判定）。
3. **重组与最终性**：每条链按自己的「安全区块」钉住；L2 的软确认消息标为「待确认」。
4. **垃圾消息**：任何链上开通了容器的人都能往你的信箱写。列表只显示元数据，不自动取载荷；
   本地静音 + 收信链位图 + 「请求」分区。
5. **元数据仍然公开**：谁在哪条链上给谁发了消息，所有人可见；内容加密。
6. **发件身份只能在本链**：第一版中，发件人必须在消息发出的那条链上持有容器。
   「用 BNB 身份在 Base 上发」需要跨链证明持有关系，放到以后的版本（可用签名代发 + 客户端按时间核对，另行设计）。
